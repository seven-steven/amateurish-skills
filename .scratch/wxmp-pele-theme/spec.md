# publish-to-wxmp：主题配置支持 Pele 图表配色

Status: ready-for-agent

## Problem Statement

发布者目前可以通过主题配置调整公众号文章的正文样式，但文章中的 Mermaid 图表经 Pele 渲染后仍使用独立的默认配色和固定白色 PNG 画布。选择文章主题不会改变图表颜色，主题作者无法在同一份主题中定义协调的图文配色，也不能正确交付深色背景图表。

仅暴露配色字段还不足以解决问题：图内已有的显式颜色需要保留，错误配置不能静默失效，主题修改后也不能继续预览或发布旧构建。现有构建过期检查只覆盖笔记内容，无法发现所选主题的变化。

这里的 Pele 是图表渲染器，不是一个待新增的文章主题。本需求是在现有主题系统中增加可选的图表配色能力。

## Solution

在现有主题 YAML 中增加可选的 `pele` 配色段。一份主题同时描述正文样式和图表配色，继续通过现有 `--theme` 或全局 `theme` 选择，不增加独立的图表主题选择参数。

主题作者可以只覆盖需要改变的颜色，包括基础配色、语义配色和最多八个系列色。首版只接受带引号的、不透明的十六进制颜色。深色主题的背景同时作用于图表配色和最终 PNG 画布。

配色优先级为：图内显式配色 > 主题配色 > Pele 默认配色。没有配置 `pele` 的主题保留现有效果和图表产物；现有内置主题不自动获得新配色，也不从正文主色自动推导图表颜色。

无效配色配置使构建失败，并给出可定位的诊断。构建记录同时识别所选主题的有效配置；主题变化后，预览、上传和推草稿要求先重新构建，不静默复用旧产物，也不自动重建。

## User Stories

1. As a 主题作者, I want 在一份主题中配置正文和图表颜色, so that 文章与图表可以拥有协调的视觉风格。
2. As a 发布者, I want 继续使用现有 `--theme` 选择完整主题, so that 不必学习另一套图表主题参数。
3. As a 发布者, I want 全局 `theme` 配置同样选择带图表配色的主题, so that 日常发布不必重复输入选项。
4. As a 主题作者, I want 沿用现有基础主题继承和深合并规则, so that 增加图表配色不必复制整份正文主题。
5. As a 主题作者, I want 所有图表配色字段均为可选, so that 可以从只修改一个强调色开始。
6. As a 主题作者, I want 分别设置背景和前景文字色, so that 可以设计浅色或深色图表。
7. As a 主题作者, I want 设置弱化文字、线条和边框颜色, so that 次要信息和结构线条与整体配色一致。
8. As a 主题作者, I want 设置节点底色和交替底色, so that 图表分组与层次清晰。
9. As a 主题作者, I want 设置强调色和关键任务颜色, so that 常规强调与关键语义可以使用不同颜色。
10. As a 主题作者, I want 设置浅底和深底上的文字色, so that 可以调整 Pele 已有的对比文字配色。
11. As a 主题作者, I want 分别覆盖 `series_1` 至 `series_8`, so that 多系列图表能够使用统一色板。
12. As a 主题作者, I want 只修改部分系列色而保留其他槽位, so that 不必为少量调整重写整个色板。
13. As a 发布者, I want 深色背景同时覆盖 PNG 画布与图表配色, so that 图表留白和边缘不会继续铺白底。
14. As a 图表作者, I want 图内 `style` 和 `classDef` 指定的颜色保留原意, so that 主题不会覆盖承载业务语义的显式颜色。
15. As a 图表作者, I want 图内 `themeVariables` 指定的系列色优先于主题色, so that 单张图的明确选择得到尊重。
16. As a 主题作者, I want 未被图内显式指定的系列槽位继续使用主题或默认色, so that 局部覆盖不会丢失其余配色。
17. As a 现有用户, I want 没有 `pele` 配置时得到与变更前相同的图表文件名、SVG 和 PNG, so that 已有内容与缓存不发生无意义变化。
18. As a 现有用户, I want 内置主题和已有正文主题行为保持不变, so that 升级不会悄悄改变文章效果。
19. As a 现有用户, I want 正文主色变化不会自动推导图表颜色, so that 图表配色始终由明确配置决定。
20. As a 发布者, I want 保留已验证的中文字体、字号和手机端布局, so that 新增配色能力不会引入缺字或布局退化。
21. As a 主题作者, I want 使用带引号的 `#RGB` 或 `#RRGGBB` 表达颜色, so that 配置简单且离线渲染结果稳定。
22. As a 主题作者, I want 未知字段、错误类型和无效颜色立即阻止构建, so that 配置错误不会伪装成发布成功。
23. As a 主题作者, I want 错误信息指出主题文件和具体字段, so that 可以直接定位拼写错误或未加引号的颜色。
24. As a 发布者, I want 无效主题即使遇到没有图表的笔记也被拒绝, so that 配置正确性不依赖当前笔记是否碰巧触发某个字段。
25. As a 发布者, I want 主题中的正文样式或图表配色变化后，旧构建被标记为过期, so that 预览和发布不会继续消费旧效果。
26. As a 发布者, I want 过期构建在预览、上传、创建草稿和更新草稿前被拒绝, so that 用户看到和发出的内容始终来自有效构建。
27. As a 发布者, I want 过期检查在图片上传、封面上传或草稿请求之前完成, so that 失败操作不会产生远端副作用。
28. As a 发布者, I want 过期提示明确要求重新 `build`，而不是自动重建, so that 内容变化仍经过现有预览与确认流程。
29. As a 发布者, I want 重建后能够正常上传和推草稿, so that 修复配置或更新主题后可以继续原有工作流。
30. As a 发布者, I want 对主题新鲜度按有效配置而非文件修改时间判断, so that 没有实际配置变化时不会被无意义地要求重建。
31. As a 发布者, I want 无关主题的修改不影响当前构建, so that 不同主题的日常维护互不干扰。
32. As a 发布者, I want 同一输入、主题和参考时间产生确定的图表产物, so that 重建结果稳定，上传缓存可以复用。
33. As a 发布者, I want 影响 PNG 的颜色变化，包括仅改变画布背景，也能产生正确的新产物与缓存身份, so that 不会因复用旧图片而丢失配色修改。
34. As a 安装后的 skill 用户, I want 配色功能继续完全离线运行且不依赖宿主字体或额外安装, so that 自包含分发和现有运行平台保持可用。
35. As a 主题作者, I want 查阅完整的配置契约和一个可用的示例主题, so that 能够自行编写配色而不必阅读实现。
36. As a 维护者, I want 通过现有 CLI 和真实渲染产物验证这些行为, so that 测试覆盖用户实际使用的发行物，而不是仅验证内部对象或 mock。

## Implementation Decisions

### 主题 Interface

- 扩展现有主题数据模型，增加可选的 `pele` 配色映射；继续沿用主题发现、基础主题继承和深合并机制，不引入另一套主题注册或选择机制。
- 主题选择优先级保持为显式 `--theme`、全局 `theme`、现有默认主题。默认主题不变。
- 开放字段及其含义如下：

  | 字段 | 含义 |
  | --- | --- |
  | `background` | 图表背景与 PNG 画布颜色 |
  | `foreground` | 主要文字颜色 |
  | `muted` | 弱化文字颜色 |
  | `line` | 线条颜色 |
  | `border` | 边框颜色 |
  | `surface` | 节点或区域的主要底色 |
  | `surface_alt` | 交替或次级底色 |
  | `accent` | 强调色 |
  | `critical` | Pele 已有关键任务语义使用的颜色 |
  | `foreground_on_light` | Pele 已有浅底对比文字颜色 |
  | `foreground_on_dark` | Pele 已有深底对比文字颜色 |
  | `series_1` 至 `series_8` | 八个独立的系列色槽位 |

- 字段映射到当前固定 Pele 版本已经支持的公开配色变量。主题只提供默认色，不保证每种图表都会使用每个字段，也不改写各图表类型已有的颜色用途。
- 所有字段均可省略；空配色映射等价于没有配色覆盖。主题未覆盖的值继续由图内设置或当前 Pele 默认值提供，不新增自动推色或补色算法。
- 字段值必须是字符串形式的 `#RGB` 或 `#RRGGBB`，大小写十六进制数字均可。主题文档要求给颜色加引号，避免 YAML 将 `#` 解释为注释。
- 使用编号字段表达系列色，不增加 YAML 列表语法或将逗号字符串作为另一套色板格式。

### 配置校验

- 在构建加载所选主题时校验 `pele`，而不是等到某个图表类型使用颜色后才发现错误。
- 非映射结构、未知字段、非字符串值、非法十六进制值及超出约定的颜色形式均使构建非零退出；不存在静默忽略或回退。
- 对已有正文主题字段保留现行兼容规则，不借此扩大对其他主题段的严格校验。
- 错误信息包含主题文件和字段名；结构错误指向 `pele` 本身，字段错误指向具体键。因未加引号而被现有解析器读成其他结构的颜色同样属于错误配置。
- 无效构建不能登记为可供后续命令消费的成功构建。

### 图表编译与产物

- 本地图表编译模块的现有 Interface 接收可选、已校验的配色输入。CLI 统一加载主题，再将配色交给图表编译模块，不在预览、上传或推草稿阶段分别修补图片。
- 保持现有 Pele、离线中文字体和栅格化链路，不通过更换图表库或升级依赖来实现配色能力。
- 使用 Pele 的公开配色变量完成主题适配；保存 SVG 前，继续把变量落实为具体样式并移除自定义属性。发布仍只嵌入 PNG。
- 优先级逐项生效：图内显式配色 > 主题配色 > Pele 默认配色。保留图内字面量样式与已指定的系列色，未指定的系列槽位仍能获得主题默认值，避免图内少量配置整体替换主题色板。
- `background` 同时控制图表背景配色和栅格化画布；省略时沿用现有白色画布。支持深色背景是显式选择，不改变默认浅色效果。
- 字体、字号、圆角、字重、布局、尺寸限制、缺字与隐藏标签等既有安全校验保持有效；配色变化不能绕过这些约束。空图检测必须区分背景与实际图表内容，不能仅因深色画布存在就判定图像非空。首版不自动检测并修正用户选择的对比度。
- 没有 `pele` 配置或配色映射为空时走保持旧行为的路径，不注入无意义样式，不改变图表资产名称、SVG 或 PNG 字节。
- 图表产物身份和缓存必须涵盖所有会影响最终图像的有效输入，尤其是 PNG 画布背景；仅改变背景也不能使同一资产身份对应不同图片。相同有效输入应得到相同产物。
- 继续保留可编辑图表源码、中间 SVG 与 PNG，原始笔记正文不因配色构建而被修改。

### 构建新鲜度

- 构建记录增加足以识别当次实际所选主题及其有效配置的指纹信息；保留既有输入归属、笔记内容和完成状态检查。
- 主题新鲜度覆盖完整有效主题，包括正文样式、已有渲染选项和 `pele` 配色，而非只比较主题名或图表字段。
- 复核以构建实际所选主题为依据，避免显式 `--theme` 与全局默认之间造成误判。比较有效配置，不以文件修改时间作为变化依据；无关主题不参与判定。
- 所选主题已发生有效变化、无法再解析或已被删除时，后续命令拒绝消费旧构建，并提示重新 `build`。缺少新鲜度信息的旧格式构建沿用现有保守策略，要求重建，不猜测其仍然有效。
- `preview`、`upload`、创建草稿和更新草稿共用新鲜度判定，在启动新预览或产生任何远端副作用前完成检查。默认构建选择与显式输出目录选择均适用。
- 不自动重建，不要求已经启动的预览进程实时监视主题文件；现有预览监听仍只负责构建产物刷新。

### 交付约束

- 同步更新主题契约、图表说明、用户说明和权威设计规格，使配置字段、优先级、背景行为和重建要求一致。
- 新增独立的示例主题展示图文配色配置，不通过修改现有内置主题来展示新能力。
- 涉及预构建引擎的修改必须经既有构建流程生成并提交发行物；安装后的 skill 继续自包含，运行时不新增安装或联网步骤。

## Testing Decisions

- 用户已确认：复用现有 `wxpush` CLI 作为唯一主测试 Seam。测试跨越调用者实际使用的 Interface，沿用现有图表测试及其 CLI 环境夹具，不新增测试专用公开 Interface。
- 自定义主题测试使用临时安装副本、笔记、配置目录和状态目录；主题发现仍基于安装目录，不增加测试专用主题目录参数。副本须包含完整的图表 bundle、字体、WASM 与资产清单，不把临时主题写入真实工作树。
- 覆盖主题加载、图表编译、产物归属与新鲜度、预览、上传和草稿消费行为。通过真实 CLI 使用提交的发行 bundle、字体和 WASM；不 mock Pele 或栅格化过程。
- 好的测试验证退出状态、诊断、实际生成文件、解码图像和可观察副作用，不绑定内部函数调用、私有对象形状、变量注入顺序或哈希实现细节。
- 先写失败测试再实现，按可观察行为逐步形成 red-green-refactor 循环。所有新增测试必须从根 `npm test` 可达；实现交付前运行完整 `npm test`，不能只运行新测试。

### 主测试矩阵

1. **选择和继承**：经显式主题选择和全局默认分别构建；自定义主题继承现有正文主题，加入 `pele` 后正文排版及已有渲染选项仍然生效。
2. **旧行为基线**：在实现前为代表性图表固定旧行为基线，控制源码、主题和参考时间；无 `pele` 配置时验证图表文件名、SVG 和 PNG 与基线一致。不能仅比较两个修改后实现的输出来自证兼容。
3. **部分覆盖**：单字段覆盖只改变对应配色；未覆盖字段保持当前默认。逐项覆盖开放字段，并为关键任务色、对比文字色和系列色选择确实使用该字段的代表性图表类型。
4. **系列色**：八个槽位可单独设置；仅指定部分槽位时，其余槽位保留默认或主题值，不因稀疏设置而被重新编号。
5. **优先级**：分别验证图内 `style`、`classDef`、初始化指令和 frontmatter `themeVariables` 的显式颜色优先；图内仅指定一个系列色时，其他槽位继续取得主题或默认色。
6. **真实图像**：解析保存的 SVG，确认配色已经落实且没有未解析变量或自定义属性；实际解码 PNG，检查有效尺寸、预期背景及可见的文字和线条，不仅断言文件头或搜索颜色字符串。
7. **深色画布**：以有对比的深色主题证明画布留白、图形、标签和连线正确；验证深色背景本身不能使空图检测通过。单独改变 `background` 后验证 PNG 与产物身份正确变化，避免背景遗漏于缓存或被固定白底覆盖。
8. **错误配置**：覆盖未知键、非映射 `pele`、错误标量类型、未加引号的颜色、非法字符与长度、透明色、颜色函数、CSS 变量、列表和超出八槽位的键。错误定位到主题文件及字段，构建失败；没有图表的笔记同样执行校验。
9. **主题变化使构建过期**：分别修改正文样式和图表配色，确认 `preview`、`upload`、创建草稿和更新草稿均拒绝旧构建。覆盖默认构建选择与显式输出目录，保留原有输入归属及失败构建回归。
10. **无远端副作用**：复用本地模拟 CDN 与草稿服务，在过期后验证图片上传、封面上传和草稿创建或更新请求数均为零；预览命令以进程退出和诊断验证，不自动打开真实浏览器或调用真实公众号。
11. **恢复与误判防护**：重建后恢复正常流程；仅改变主题文件修改时间、保持有效配置不变或修改无关主题不使当前构建失效；缺失主题和缺少指纹的旧格式构建要求重建。
12. **确定性与分发**：同一输入、有效主题和参考时间重复构建得到相同图表产物；从独立安装目录验证配色能力仍可离线运行，保留现有 macOS 与无桌面 Linux 的验证范围。

### Prior Art

- 现有主题回归已通过真实 CLI 验证内置主题、自定义 YAML、基础主题继承和微信兼容样式输出，新增主题配置应沿用该模式。
- 现有图表回归已覆盖真实 PNG 解码、SVG 变量展开、确定性重建、失败构建、本地模拟上传与草稿、独立安装和离线运行，新增配色与新鲜度用例复用这些测试夹具。
- 现有浏览器回归检查手机与宽屏下的真实文章布局；保留其回归覆盖，必要时消费同一 CLI 构建产物补充配色场景，不将浏览器内部函数作为另一个主测试 Seam。
- 真实公众号后台和手机上的最终视觉确认仍遵守现有发布流程；自动测试不请求真实公众号，也不替代人工发布确认。

## Out of Scope

- 新增一个名为 `pele` 的文章主题，或将任何新主题设为默认。
- 独立的图表主题配置文件、全局配色段、命令行配色参数或另一个图表主题选择系统。
- 从正文 CSS、正文主色或系统明暗模式自动推导图表配色。
- 修改现有内置主题的图表效果，或重新设计现有正文主题系统与继承范围。
- 字体、字号、圆角、字重、布局和图表尺寸的可配置化。
- 透明色、CSS 颜色名称、颜色函数、CSS 变量、任意 CSS 注入和 YAML 列表扩展。
- 新增图内主题语法、强制覆盖图内显式颜色，或扩展 Pele 当前不支持的 Mermaid 行为。
- 自动修正低对比度配色、自动补色或提供视觉主题编辑器。
- 更换或升级图表渲染库，调整微信服务端协议、认证或草稿业务行为。
- 自动重建过期构建、运行中的预览自动监听主题源文件、自动上传或自动发布。
